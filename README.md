# Road Damage Detection (RDD) — GIS & Geolocation Backend Layer

> **Architecture Notice:** The `backend/` package is an **independent GIS enrichment layer** built on top of the existing `rdd_dedup` pipeline. It does **not** alter, refactor, or couple with `rdd_dedup` detection, tracking, or deduplication logic. It operates strictly as a downstream consumer of completed survey outputs.

---

## 1. Overview & Purpose

The GIS backend enables post-survey geolocation enrichment of detected road defects. After a video has been processed by the computer vision and deduplication pipeline, the user can supply a companion GPX survey file.

This layer:
1. Reads actual video frame rate (FPS) and timing directly from the video file.
2. Parses and validates GPX GPS trackpoints and ISO-8601 timestamps.
3. Synchronizes video playback time with the GPX survey timeline.
4. Locates the exact geographic coordinates (Latitude, Longitude) of each unique defect by linearly interpolating between surrounding GPX points at the defect's `max_confidence_frame`.
5. Resolves and encodes the representative defect crop image patch (base64 data URI).
6. Generates a standard RFC 7946 **GeoJSON FeatureCollection** (`defects.geojson`) containing both defect point features and the survey trajectory line.
7. Produces a self-contained interactive Leaflet.js map for rendering in the Gradio web UI.

## 3. Input Files

| Input | Required | Description |
| :--- | :---: | :--- |
| **Video File** (`.mp4`) | **Yes** | The survey footage. Used to probe actual video FPS and total frame count via OpenCV. |
| **GPX File** (`.gpx`) | **Yes** | GPS track log recorded during the survey containing `<trkpt lat="..." lon="...">` with child `<time>` elements. |
| **`summary.json`** | **Yes** | The output artifact generated by `rdd_dedup` containing `finalized_defects`, their `defect_type`, `max_confidence`, and `max_confidence_frame`. |
| **Defect Crops** (`crops/*.jpg`) | Optional | Saved peak-confidence image patches for each defect. Embedded as base64 in tooltips. |

## 4. Video-to-GPX Synchronization Method

Defects in `summary.json` are recorded using video frame numbers. To convert frame numbers to geographic coordinates, the backend converts frames to relative seconds, then to absolute UTC timestamps:

$$\text{video\_time\_seconds} = \frac{\text{representative\_frame}}{\text{FPS}}$$

Where:
* **$\text{representative\_frame}$** is strictly `max_confidence_frame` from the existing pipeline.
* **$\text{FPS}$** is the actual video stream frame rate read via OpenCV (`cv2.CAP_PROP_FPS`), not assumed or hardcoded.

### Establishing the Temporal Anchor:
1. **Explicit Video Start Time (`video_start_time`):** If provided (or stored in container metadata), video time is added directly to this UTC timestamp.
2. **Configurable Time Offset (`offset_seconds`):** If the camera started $N$ seconds before or after the GPS recorder started:
   $$\text{video\_start\_time} = \text{gpx\_start\_time} + \text{offset\_seconds}$$
3. **Default Alignment (`auto_align_gpx_start`):** When no offset or manual start timestamp is provided, the backend assumes video frame 0 aligns with the first GPX point. This assumption is explicitly documented and reported in the run's sync metadata warnings.

$$\text{defect\_absolute\_time} = \text{video\_start\_time} + \text{timedelta}(\text{seconds}=\text{video\_time\_seconds})$$

## 5. GPS Interpolation Method

GPS receivers typically record at 1 Hz (once per second), while video runs at ~30 FPS. Simply assigning the nearest GPX point introduces spatial stepping artifacts.

For any target timestamp $t_{\text{defect}}$ between two adjacent GPX points $P_1(t_1, \text{lat}_1, \text{lon}_1)$ and $P_2(t_2, \text{lat}_2, \text{lon}_2)$:

1. Compute time fraction:
   $$\alpha = \frac{t_{\text{defect}} - t_1}{t_2 - t_1}, \quad 0 \le \alpha \le 1$$
2. Linearly interpolate coordinates:
   $$\text{latitude}_{\text{defect}} = \text{lat}_1 + \alpha \cdot (\text{lat}_2 - \text{lat}_1)$$
   $$\text{longitude}_{\text{defect}} = \text{lon}_1 + \alpha \cdot (\text{lon}_2 - \text{lon}_1)$$
3. If elevation or speed are present in both points, they are interpolated using the same factor $\alpha$.
4. **Boundary Tolerance:** If a defect occurs within a small tolerance window ($\le 3.0$ seconds) before GPX start or after GPX end, coordinates are safely clamped to the start/end point with a warning notice. If outside this window, an error is reported.

## 7. Gradio Frontend Integration

In `temp_frontend/gradio_ui.py`:
1. When video processing completes, an expandable accordion appears: **"🗺️ Geolocation & GIS Map Enrichment"**.
2. The user uploads/selects their `.gpx` file.
3. The user clicks **"📍 Generate GEO Information"**.
4. The frontend invokes `backend.geo_service.enrich_inspection_with_gis(...)`.
5. The backend generates `defects.geojson` and returns the interactive Leaflet.js HTML map with embedded defect crop images and hover cards.
6. The user can interact with the map, hover over markers, inspect defect crops, and download `defects.geojson`.

## 9. Known Limitations & Edge Cases

1. **Camera Clock Drift:** If camera internal clock and GPS clock drift significantly on multi-hour recordings, linear time stretching or frequent sync checkpoints may be needed in V2.
2. **Missing Video Timestamps:** Standard MP4 containers compressed via social media/messaging (e.g. WhatsApp) strip original EXIF creation timestamps; the user should provide simultaneous start footage or specify `offset_seconds`.
3. **Tunnel / Signal Loss:** If GPS receiver loses satellite fix during video capture, interpolation across long temporal gaps will assume a straight line between the last known fix and reconnection.
